验收：3个示例都能打开当前Android支持的目标；离线界面不暗示可以自由问答；演示取消/返回正常。这里只优化展示入口，不改变模块可用性规则。

## 三、版本号收敛

### 已核对事实

- 应用pubspec为1.2.14+9。
- 当前离线脚本输入build-number=2010，实际ARM64 APK为versionName=1.2.14、versionCode=4010。
- 脚本在构建前比较输入值与登记历史，构建后读取APK实际值，但未再次核对预期版本及递增关系。
- 关于页已通过平台包信息读取实际版本，不需要再改为读取pubspec。

### 建议统一规则

| 数据 | 唯一职责 |
| --- | --- |
| versionName | 从应用pubspec读取，例如1.2.14；变更面向用户的版本时显式更新 |
| Android versionCode | Android发行入口显式指定最终值，不要求操作者计算ABI偏移 |
| APK实际值 | 构建后读取并严格验证，是交付事实来源 |
| 关于页与复制内容 | 从已安装包读取，必须与该APK一致 |
| 冻结manifest、文件名、台账 | 校验成功后统一采用实际值；旧包及其记录不回填修改 |

### 脚本调整方案

将发行入口改为含义明确的--version-code。不要静默把旧--build-number参数按新含义处理：旧参数应拒绝并给出迁移说明，防止习惯输入2011而构建出可安装版本降低的包。

项目固定Flutter 3.47.8已有支持：

- Flutter命令--android-project-arg接受key=value并转为Gradle -P参数。
- FlutterPluginUtils中的force-version-code-ignoring-abi可关闭ABI versionCode加值。

因此建议该Android离线命令同时传入--build-number=<目标versionCode>和--android-project-arg=force-version-code-ignoring-abi=true，继续使用ARM64分包、既有签名和离线配置。仅对本发行入口显式设置，不改全局SDK或其他平台工作流。必须通过实际构建验证这一参数路径，不能仅凭源码判为已生效。

构建前：

1. 校验目标值、预期versionName、发行配置与输出目录未占用。
2. 汇总已登记产物、已冻结的本地候选manifest及已核对商店记录中的实际versionCode，要求目标大于同应用身份下已使用的最高值。未知后台状态单列，不猜测最新商店值。
3. 在编译前完成必要的签名配置和公开证书指纹检查，不输出密钥。

构建后：

1. 读取APK applicationId、versionName、versionCode、ABI、签名和权限。
2. 实际versionCode必须等于输入目标，versionName必须等于预期，且实际值仍大于历史最高值。
3. 身份、ABI、离线权限、签名或版本不一致时失败，不将产物登记为可发布候选。
4. 通过后冻结APK、manifest和SHA256；登记新产物，不改写历史4010及之前的记录。

当前本地最高已知候选为4010。若核对后没有更高已使用值，下一候选可采用1.2.14/4011；这是建议值，不是已冻结的版本。pubspec中的+9仍是默认开发构建值，本Android发行路径必须显式覆盖，不能把它作为已发布构建号展示。

SDK事实来源：.release/toolchains/flutter-3.47.8/packages/flutter_tools/lib/src/runner/flutter_command.dart的android-project-arg；gradle/src/main/kotlin/FlutterPluginUtils.kt的force-version-code-ignoring-abi；FlutterPlugin.kt的ABI偏移分支。
